# sdd-power — журнал версий

## v3.1 — упрощение обвязки и честный валидатор

Правки по итогам прогонов v3 на реальных проектах: меньше файлов в скилле, меньше ложного шума в валидаторе, закрытые дыры в описании.

### Что изменилось

- **Скрипты собраны в одну директорию.** `scripts/lib/*.awk` → `scripts/*.awk`, `archive.awk` растворён в `sdd.sh`: четыре файла вместо пяти, на один уровень вложенности меньше.
- **Коды возврата переосмыслены.** Ненулевой код теперь означает сбой самого скрипта (нет аргумента, нет файла, нет шаблонов), а вердикт живёт в тексте вывода. Раньше `check` и `validate` возвращали 1 на находках, и обёртка не отличала «нашлись предупреждения» от «скрипт не запустился».
- **Свежий `init` больше не шумит.** Валидатор распознаёт нетронутый шаблон PLAN и пропускает проверки содержания с одним предупреждением вместо десятка находок по заглушкам.
- **Задача без номера `<этап>.<N>` — ошибка, а не предупреждение.** Без номера нечем сверить закрытие с WORKLOG, то есть главная проверка отключается молча.
- **`archive-tasks` предупреждает о незакрытых задачах** в переносимом этапе: закрытого этапа с открытыми задачами не бывает.
- **Поиск скилла ограничен глубиной** (`find … -maxdepth 6`) и закавычен — на больших домашних директориях команда из SKILL.md выполнялась минутами.

### Что уточнено в скилле

- Раздел **«Состав скилла»**: какой файл когда нужен и какие не надо читать вовсе (`sdd.sh` вызывается, а не читается).
- Развилка **«документации нет вовсе»**: скилл дисциплинирует работу *по* доке; строить план не на чём — либо пользователь приносит ТЗ, либо требования фиксируются хотя бы страницей. Иначе «Основание» у задач пустое и проверка покрытия теряет смысл.
- **Ручной путь ставит якорь вручную** — без строки `<!-- sdd-power -->` в CLAUDE.md проект не подхватится в следующей сессии.
- **Нет git — нет тега `stage/<ID>`**: шаг пропускается, но отмечается в саммари, потому что тогда единственная точка возврата к состоянию этапа — даты записей WORKLOG.
- **Приоритет LESSONS над докой сужен** до правил, описывающих уже доказанное расхождение. Во всём остальном приоритет за документацией, а смена подхода — решение пользователя.

## v3 — заимствования из OpenSpec

Внедрены пять пунктов: валидатор трекинга, детекция дрейфа документации, `next`, верификация в трёх измерениях, перенос состава закрытого этапа.

### Проверка ТЗ до реализации

ТЗ (список из пяти пунктов) содержал девять дефектов; ниже — что найдено и как исправлено при реализации.

| # | Дефект ТЗ | Доказательство | Решение |
|---|---|---|---|
| 1 | «`[x]` без записи в WORKLOG» невыполнимо как записано: связи между задачей и записью нет | шаблон PLAN давал задачи без номеров (`- [ ] **<задача>**`), WORKLOG на них не ссылается | нумерация задач внесена в шаблон как требование; проверка — предупреждение и только для нумерованных задач, иначе старые проекты краснеют целиком |
| 2 | Коллизия пространств имён: ID этапа и номер задачи совпадают | в Threadkeep есть и этап `0.5`, и задача `0.5` | задача ключуется парой (этап, номер); поиск в WORKLOG — по токену с проверкой соседних символов, чтобы `§17.1` не считался упоминанием задачи `17.1` |
| 3 | «Статус вне набора» как ошибка даёт ложные срабатывания | реальные строки вида `**решён 29.07:** git init сделан…` — статус со свободным хвостом | проверка на вхождение ключевого слова, уровень — предупреждение |
| 4 | Без легализации задач вне ТЗ правило «Основание обязательно» шумит на инфраструктуре и тулинге | задачи вроде `git init` основания в доке не имеют | добавлен явный escape `Основание: вне ТЗ — <причина>`, признаётся валидатором |
| 5 | П.3 создавал второй источник истины о снимке | дата снимка есть в шапке PLAN и появлялась бы в конфиге | `config.yml` + `docs.lock` — машинная истина, шапка PLAN — человеческая; валидатор сверяет их и ругается на расхождение |
| 6 | YAML в bash надёжно не парсится | — | плоский формат `ключ: значение` и отдельный `docs.lock` (`sha256␠путь`) |
| 7 | П.3 красил бы все существующие проекты | в них нет `config.yml` | отсутствие конфига — предупреждение с подсказкой, а не отказ |
| 8 | П.9 противоречил действующему правилу скилла | «закрытого этапа с красным DoD не существует» против «предупреждения не блокируют» | разведено по уровням: критично блокирует, предупреждение обязано осесть задачей или строкой в «Важно знать дальше», предложение уходит в «Предложения по улучшению» |
| 9 | П.10 ломал ссылки и был деструктивен | WORKLOG и LESSONS ссылаются на номера задач; вырезание раздела из PLAN оставляло их висеть | в PLAN остаётся заголовок с пометкой «закрыт» и ссылкой, номера в архиве сохраняются дословно; команда делает `PLAN.md.bak`, идемпотентна и отказывается работать без саммари этапа |

Побочно найден фактический дефект в самом Threadkeep: шесть этапов, пять строк DoD — у этапа 3 её нет. Валидатор его показывает.

### Что появилось

- **`sdd.sh validate`** — структурная проверка содержания: DoD этапов, соответствие PLAN ↔ TIMELINE, саммари и теги закрытых этапов, `[x]` без записи в WORKLOG, задачи без основания и проверки, статусы вне наборов, бюджет LESSONS, длина записей WORKLOG, дубли номеров, число задач в `[~]`. Ошибки блокируют, предупреждения — нет. Строгость растёт по мере приближения этапа: у ещё не детализированного этапа те же находки — предупреждения.
- **`sdd.sh snapshot --docs "..."`** и `config.yml` + `docs.lock` — снимок документации фиксируется хешами; `check` каждую сессию сам сообщает, какой файл доки изменился, и требует ре-синхронизации плана.
- **`sdd.sh next`** — текущий этап, его DoD, прогресс, следующая задача целиком и заготовка записи WORKLOG с датой. Страховка после `/compact` и в оборванной сессии.
- **`sdd.sh archive-tasks <ID>`** — состав закрытого этапа уезжает из PLAN в `stages/<ID>-<имя>.md`; PLAN остаётся ответом на вопрос «что предстоит». На Threadkeep: 217 строк → 185 после закрытия одного этапа.
- **Раздел «Верификация» в шаблоне саммари** — полнота, корректность, когерентность, с уровнями находок.
- `check` теперь отвечает сразу на три вопроса: цела ли инфраструктура, не разошлась ли дока со снимком, нет ли ошибок в трекинге.

### Совместимость

Формат файлов не менялся. Новое: нумерация задач (без неё часть проверок пропускается с предупреждением), `config.yml` и `docs.lock` (создаются `init`/`snapshot`). Существующие проекты работают без изменений; `init` только дополняет недостающее.

### Проверено на стендах

Чистый проект (валидатор зелёный сразу после `init`); Threadkeep с файлами в корне под git (перенос с сохранением истории, валидатор нашёл настоящий дефект и ни одного ложного); намеренно сломанный трекинг (сработали все 14 проверок); полный цикл закрытия этапа с переносом состава и повторным прогоном; дрейф документации (правка ТЗ ловится хешем); повторные запуски всех команд.

## v2 — исполняемая инфраструктура

Диагноз: скилл описывал инфраструктуру прозой, не давая ни одной исполняемой команды, ни пути к своим шаблонам, ни проверки результата — агент «выполнял» шаг, рассказывая о нём в ответе.

| # | Что было сломано | Что сделано |
|---|---|---|
| 1 | «Создай `docs/sdd-power/`, скопируй шаблоны из `assets/`» — путь скилла агенту неизвестен | `scripts/sdd.sh`, самолокализующийся по `BASH_SOURCE`, плюс ручной фолбэк |
| 2 | Развёртывание стояло после изучения доки и перед ожиданием подтверждения плана | вынесено в шаг 1, до всего остального |
| 3 | Не было проверки результата | гейт: первый ответ сессии обязан содержать вывод `check` |
| 4 | `stages/` упоминалась в скобках; имя файла в двух местах разное | создаётся при `init`, проверяется, имя везде `<ID>-<имя>.md` |
| 5 | Старые проекты не подхватывались | императивный якорь `<!-- sdd-power -->` в CLAUDE.md и AGENTS.md, проверяется каждую сессию |
| 6 | Миграция предписывалась «молча» и без команд | `init` подбирает файлы из корня, `docs/`, `.sdd/` через `git mv` |
| 7 | `docs/sdd-power/` принудительно уходила в `.gitignore` | по умолчанию версионируется; вынос — осознанный `init --gitignore` |
| 8 | Не описан случай «проекта на диске нет» | добавлен раздел про работу в чате и присланные файлы трекинга |

## Установка

```bash
cp -r sdd-power ~/.claude/skills/            # глобально для Claude Code
chmod +x ~/.claude/skills/sdd-power/scripts/sdd.sh
```

Подъём существующего проекта:

```bash
bash ~/.claude/skills/sdd-power/scripts/sdd.sh init     --root /путь/к/проекту
bash ~/.claude/skills/sdd-power/scripts/sdd.sh snapshot --root /путь/к/проекту --docs "docs/ТЗ.md"
bash ~/.claude/skills/sdd-power/scripts/sdd.sh validate --root /путь/к/проекту
```
