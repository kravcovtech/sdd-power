# SDD Power

*[English version](README.en.md)*

Скилл для Claude Code: дисциплина длительной разработки по существующей проектной документации — с персистентным трекингом состояния, валидатором трекинга и критической проверкой самой документации.

Он нужен там, где работа не укладывается в одну сессию: агент возвращается к проекту через неделю с пустым контекстом и должен за минуту понять, что сделано, что осталось и почему когда-то приняли именно это решение.

**Версия 3.1** — трекинг исполняемый: один скрипт разворачивает инфраструктуру, валидатор проверяет содержание файлов, снимок документации ловит дрейф по хешам. Что и почему менялось по версиям — в [CHANGELOG.md](CHANGELOG.md).

## Зачем это нужно

Скилл лечит две болезни долгой разработки с агентом.

**Потеря состояния между сессиями.** Контекст обнуляется. Через неделю ни агент, ни человек не помнят, на чём остановились и почему выбрали такой подход. Лечится четырьмя файлами трекинга, которые обновляются в тот же момент, что и код — не «потом».

**Слепое доверие документации.** Документацию писали люди, она устаревает и содержит ошибки. Агент, исполняющий ошибочную доку буквально, производит баги, которые потом трудно объяснить. Лечится протоколом проверки с объективным критерием: ошибка — только то, что можно доказать фрагментом кода, двумя противоречащими абзацами или ошибкой выполнения. «Я бы сделал иначе» ошибкой не является и идёт в «Предложения по улучшению».

Обе части работают только вместе с дисциплиной. Одно «допишу потом» — и файлам больше нельзя верить, а значит, они бесполезны. Отсюда главное правило скилла: **трекинг существует на диске или не существует вовсе**. План, изложенный в чате, исчезает вместе с сессией.

## Как это устроено

Состояние живёт в `docs/sdd-power/`. Роли файлов не пересекаются — это защита от того, чтобы одно и то же расползлось по трём местам:

| Файл | Отвечает на вопрос | Природа |
|---|---|---|
| `PLAN.md` | Что предстоит сделать? | Живой документ, переписывается |
| `WORKLOG.md` | Что и почему было сделано? | Append-only, новые записи сверху |
| `TIMELINE.md` | Где мы в целом? | Таблица этапов |
| `LESSONS.md` | На чём мы уже обжигались? | Курируемый, жёсткий бюджет |
| `stages/<ID>-<имя>.md` | Что представляет собой закрытый этап? | Пишется один раз при закрытии |

По умолчанию директория **версионируется вместе с кодом**: файлы переживают свежий клон, видны коллегам и откатываются вместе с веткой. Плата — шум в диффах PR; кому важны чистые диффы, `init --gitignore` выносит трекинг из git, но тогда всё важное команде обязано доезжать до кода, документации или CLAUDE.md.

Несколько решений, которые отличают это от «веди TODO-файл»:

- **Инфраструктура разворачивается первым действием** — до изучения доки, до плана, до вопросов. Первый ответ сессии обязан содержать вывод `check`: рассказ о созданных файлах не заменяет созданных файлов.
- **Правила, которые можно проверить механически, стали проверкой.** `validate` разбирает содержание: этап без DoD, этап в плане без строки в TIMELINE, «завершён» без саммари, `[x]` без упоминания задачи в WORKLOG, задача без основания и без строки «Проверка», бюджет LESSONS, длина записей, дубли номеров. Ошибки блокируют, предупреждения — нет.
- **Строгость растёт по мере приближения.** У этапа, который ещё «детализируется при подходе», отсутствие DoD — предупреждение; у этапа в работе — ошибка.
- **Дрейф документации ловится хешами.** `snapshot` фиксирует пути и SHA-256 файлов доки, `check` каждую сессию говорит, какой файл изменился, и требует ре-синхронизации плана.
- **Покрытие проверяется в обе стороны.** Каждая задача ссылается на раздел документации, и каждое требование документации либо покрыто задачей, либо явно вынесено в «Вне объёма» с причиной. Задача нумеруется как `<этап>.<N>` — без номера валидатор не может сверить закрытие с ворклогом, поэтому это ошибка.
- **DoD этапа проверяется командами**, а не суммой галочек, и дополняется верификацией в трёх измерениях: полнота, корректность, когерентность («решили одно, в коде другое» — самая дорогая находка, потому что незаметна для тестов).
- **`[x]` только при наблюдаемом подтверждении.** «Должно работать» и «изменение тривиальное» доказательствами не считаются — иначе файлы начинают врать, а цена вранья в них нулевая.
- **PLAN не копит историю.** При закрытии этапа `archive-tasks` переносит его состав в саммари, оставляя в плане заголовок со ссылкой; номера задач сохраняются дословно, поэтому ссылки из WORKLOG и LESSONS продолжают работать.
- **LESSONS.md — правила, а не журнал багов.** «Баг #14 закрыт 12.03» ничему не учит. «Не буферизуй полный результат перед экспортом — OOM на отчётах >10MB, используй стриминг» — применимо к новому коду. Бюджет — 20 правил и ~120 строк, потому что файл читается целиком каждую сессию.
- **Скоуп держится.** Замеченное попутно дублирование и мёртвый код идут задачей в PLAN.md, а не в текущий дифф. Исключение — если находка физически блокирует задачу.
- **Старые проекты подхватываются.** `init` подбирает файлы трекинга из корня, `docs/`, `.sdd/` (через `git mv`, с сохранением истории) и ставит якорь `<!-- sdd-power -->` в CLAUDE.md — по нему скилл активируется даже в сессии, где не сработал по фразе пользователя.

## Команды

Всё делает один идемпотентный скрипт — существующие файлы он не перезаписывает:

```bash
SDD=~/.claude/skills/sdd-power

bash "$SDD/scripts/sdd.sh" init --name "Проект"        # развернуть или подобрать существующее
bash "$SDD/scripts/sdd.sh" check                        # начало сессии: инфраструктура + дрейф доки + ошибки трекинга
bash "$SDD/scripts/sdd.sh" next                         # где остановились, что следующее, заготовка записи WORKLOG
bash "$SDD/scripts/sdd.sh" validate                     # полный разбор содержания файлов
bash "$SDD/scripts/sdd.sh" snapshot --docs "docs/ТЗ.md" # зафиксировать снимок документации
bash "$SDD/scripts/sdd.sh" stage 2 auth                 # заготовка саммари закрытого этапа
bash "$SDD/scripts/sdd.sh" archive-tasks 2              # перенести состав этапа из PLAN в саммари
```

Корень проекта берётся из `git rev-parse --show-toplevel`, иначе — текущая директория; задать явно — `--root DIR`. Скрипт вызывает сам агент; вручную он нужен разве что для разового подъёма старого проекта.

Без bash скилл работает в ручном режиме — SKILL.md содержит те же шаги обычными командами, но валидатор и детекция дрейфа будут недоступны.

## Чего он не делает

- Это дисциплина, а не автопилот. Файлы ценны ровно настолько, насколько честно они заполняются; агент, который поставил `[x]` без проверки, ломает систему быстрее, чем её отсутствие.
- Валидатор проверяет структуру и связность, а не смысл. Он поймает этап без DoD и галочку без записи в ворклоге, но не отличит честную запись от выдуманной.
- Он не заменяет документацию и не пишет её за вас. Нет внятного источника требований — скиллу не на чем строить план.
- Он не решает архитектурные развилки сам. Вопросы, чей ответ меняет модель данных, эскалируются пользователю до начала кода.
- Он избыточен для разовой мелкой правки в одну сессию — для неё разворачивать церемонию не нужно.

## Установка

```bash
git clone https://github.com/kravcovtech/sdd-power.git ~/.claude/skills/sdd-power
chmod +x ~/.claude/skills/sdd-power/scripts/sdd.sh
```

Windows (PowerShell):

```powershell
git clone https://github.com/kravcovtech/sdd-power.git $env:USERPROFILE\.claude\skills\sdd-power
```

Для одного проекта — клонируйте в `.claude/skills/sdd-power` внутри репозитория.

Английская версия лежит в `en/` и ставится копированием этой директории — см. [README.en.md](README.en.md).

Перезапустите Claude Code. Скилл подхватится сам на фразах вроде «начни разработку по документации» или «продолжи с места остановки», а также если в проекте уже есть `docs/sdd-power/` или якорь в CLAUDE.md.

## Как использовать

**Первая сессия** — инициализация:

> Начни разработку по документации в `docs/`

Агент первым действием развернёт `docs/sdd-power/` и покажет вывод `check`, затем прочитает документацию критическим взглядом, разложит требования на этапы и пронумерованные задачи, зафиксирует снимок доки, покажет найденные расхождения и открытые вопросы — и дождётся вашего подтверждения плана до первой строки кода.

**Любая следующая сессия** — продолжение:

> Продолжи разработку

Агент прогонит `check`, сверит файлы с фактическим состоянием кода (файлы могут врать — работу могли делать мимо него), разберёт незакрытые `[~]` и в двух предложениях скажет, где остановились и что идёт следующим.

Полезные фразы: «сверься с планом», «проверь трекинг», «зафиксируй прогресс», «где мы остановились», «закрой этап».

## Подъём существующего проекта

Если разработка уже идёт, а трекинга нет или он лежит по старым путям:

```bash
bash ~/.claude/skills/sdd-power/scripts/sdd.sh init     --root /путь/к/проекту
bash ~/.claude/skills/sdd-power/scripts/sdd.sh snapshot --root /путь/к/проекту --docs "docs/ТЗ.md"
bash ~/.claude/skills/sdd-power/scripts/sdd.sh validate --root /путь/к/проекту
```

`init` идемпотентен: подберёт файлы от прежних версий скилла, создаст недостающее и ничего не затрёт. `validate` на реальном проекте обычно сразу находит настоящие дефекты — этап без DoD, закрытую задачу без следа в ворклоге.

## Структура репозитория

```
.
├── README.md                         # русская версия
├── README.en.md                      # английская версия
├── CHANGELOG.md                      # что менялось по версиям и почему
├── LICENSE
├── SKILL.md                          # ядро: режимы, протокол, правила обновления
├── scripts/
│   ├── sdd.sh                        # init, check, validate, next, snapshot, stage, archive-tasks
│   ├── validate.awk                  # разбор содержания файлов трекинга
│   └── next.awk                      # текущий этап, прогресс, следующая задача
├── assets/                           # шаблоны файлов трекинга
│   ├── PLAN.template.md
│   ├── WORKLOG.template.md
│   ├── TIMELINE.template.md
│   ├── LESSONS.template.md
│   └── STAGE.template.md
├── references/
│   └── docs-verification.md          # пограничные случаи: ошибка доки или вкусовщина
└── en/                               # английская копия скилла (документация; версия 2)
    ├── SKILL.md
    ├── assets/
    └── references/
```

Русская версия лежит в корне, чтобы обычный `git clone` в `~/.claude/skills/` ставил её напрямую.

`references/docs-verification.md` подгружается только при сомнении — тест на объективность, каталог типов ошибок с примерами, разбор пограничных случаев (дока требует небезопасного; дока противоречит рабочему коду; ошибка найдена в уже реализованной части) и формат эскалации.
